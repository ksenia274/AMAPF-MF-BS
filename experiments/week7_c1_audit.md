# Неделя 7, этап C1: аудит оптимальности по makespan

Что требуется: ни одно наше изменение не должно менять найденный T (makespan), и это должно быть видно либо из кода,
либо из проверки перебором. Код в этом этапе не менялся. Строки — по коммиту a70d321.

Слова, которые нужны ниже:
- **сеть «клетка × время»**: вершина — (клетка, шаг). Bulk Search ищет в ней пути от стартов до целей так же, как
  алгоритм максимального потока: каждый найденный путь добавляет одного робота, путь может «отменять» части уже
  проложенных путей (обратные рёбра);
- **пачка (bulk)**: отрезок шагов одной клетки, через который подряд не проходит ни один уже проложенный путь
  (`blocks[cell]` — шаги, где клетка занята). Вершины пачки соединены бесплатными ожиданиями, поэтому Bulk Search
  раскрывает пачку целиком одним узлом очереди: «вход в момент t» значит «доступны шаги от t до конца пачки»;
- **кусок (bscut)**: пачка, дополнительно разрезанная мягкими разрезами (`softCuts`): шаги, когда в клетке чужой
  робот. Кусок раскрывается одним узлом так же, как пачка;
- **посещённость**: `visitedTimeSTeps[cell]` — шаги, с которых клетку уже раскрывали в этом поиске.

## 1. Главный вопрос: может ли поздний дешёвый вход закрыть пачку и потерять пути

### Ответ

**Нет, не может.** Поздний вход закрывает только шаги от себя и дальше. Более ранний вход в ту же пачку после этого
не отбрасывается, а раскрывает оставшийся кусок «от себя до позднего входа − 1». Вместе они покрывают те же шаги,
что покрыл бы один ранний вход. Порядок очереди (штраф у bspen и bscut, `timeStep + h` у bs) влияет только на то,
*какой* путь найдётся, но не на то, *найдётся ли* он. Значит, при данном T ответ «пути нет» одинаков для всех
трёх вариантов. Это та же проверка, что в исходном Bulk Search, разница только в порядке очереди.

### Код (bs_team.hpp)

Посещённость хранится как множество шагов. Ключ сравнения — только шаг (стр. 420):
```cpp
bool operator<(const TimestepCostPair &b) const { return timeStep < b.timeStep; }
```
Порядок очереди: штраф первым, потом `key = timeStep + h` (стр. 431). Для bs штраф всегда 0.
```cpp
bool operator()(const Node &a, const Node &b) const { return a.pen != b.pen ? a.pen > b.pen : a.key > b.key; }
```
Проверка при снятии узла с очереди, `checkTimestepAndGetUnvisitedSafeInterval` (стр. 552-588):
```cpp
int prevBlock = -1, nxtBlock = maxTimestep;          // границы пачки, в которой лежит шаг ts
...
if (cutMode)                                          // bscut: границы куска, а не пачки
{
    nxtBlock = min(nxtBlock, nextSoftCut(cellID, timeStepCostPair.timeStep));
    prevBlock = max(prevBlock, prevSoftCut(cellID, timeStepCostPair.timeStep));
}
auto itrt = visitedTimeSTeps[cellID].upper_bound(TimestepCostPair(timeStepCostPair.timeStep));
if (itrt != visitedTimeSTeps[cellID].begin())
{
    --itrt;
    if (itrt->timeStep > prevBlock)                   // (А) в этой пачке уже был вход не позже ts
        return make_pair(false, Interval());
    ++itrt;
}
if (itrt != visitedTimeSTeps[cellID].end() && itrt->timeStep <= nxtBlock)
{                                                     // (Б) в этой пачке был вход ПОЗЖЕ ts
    nxtVisitedTimestep = itrt->timeStep;
    return {true, Interval(timeStepCostPair.timeStep, nxtVisitedTimestep - 1)};
}
return {true, Interval(timeStepCostPair.timeStep, nxtBlock)};
```
Отметка ставится после раскрытия (стр. 944): `visitedTimeSTeps[currentCell].insert(timeStepCostPair);`.
Проверка при добавлении в очередь `checkTimestep` (стр. 589-610) — то же правило (А).

### Разбор по шагам

Пусть в пачке (или куске) с границами (prevBlock, nxtBlock] есть вход e (ранний) и вход l (поздний), e < l.

1. Сначала раскрыт l (у него меньше штраф). Он получает отрезок [l, nxtBlock] и отмечает шаг l.
2. Потом снимается e. Правило (А) смотрит на последний отмеченный шаг ≤ e. Шаг l больше e, поэтому (А) не
   срабатывает, и e **не отбрасывается**. Срабатывает (Б): e получает отрезок [e, l − 1].
3. Вместе: [e, l − 1] ∪ [l, nxtBlock] = [e, nxtBlock]. Это ровно то, что дал бы один e, раскрытый первым.

Правило (А) отбрасывает вход только тогда, когда в той же пачке уже раскрыт вход **не позже** его. Значит, его
шаги уже покрыты. Так получается, что в любой момент раскрытые шаги пачки — это [самый ранний раскрытый вход,
конец пачки]. Это не зависит от порядка снятия.

Почему от порядка не зависит и сам ответ «путь есть / пути нет»:
- из раскрытого отрезка [l, h] следующие узлы строятся только по клетке, отрезку и флагу `blockedToMove`
  (ходы в соседей `getAllTimeSteps`, обратное ожидание, стр. 953-956; переход через мягкий разрез, стр. 948-951).
  Штраф на это не влияет, он только складывается в поле `pen`;
- если отрезок разбит на два, [e, l − 1] и [l, h], то каждый ход из исходного отрезка есть в одной из половин.
  Узлов в очереди может стать больше, но ни один шаг не теряется;
- значит, поиск обходит все шаги сети, достижимые из стартов. Это обычный поиск в графе, и порядок обхода на
  множество достижимых вершин не влияет. Сток (свободная цель, стр. 938-943) достижим при любом порядке или ни при
  каком. Поиск останавливается на первом найденном стоке, а это зависит только от достижимости;
- каждый найденный путь увеличивает поток на 1. Максимальный поток не зависит от того, в каком порядке находились
  увеличивающие пути. Значит, «вся команда дошла за T» тоже не зависит от порядка, и T тот же.

bscut отличается только тем, что пачка разрезана на куски (`prevSoftCut`/`nextSoftCut`). Для куска верно то же
рассуждение, а переходы между кусками есть явно:
- ожидание через разрез (стр. 948-951);
- вход в начало каждого куска `max(soft + 1, firstMove)` (стр. 620-628);
- обход запрещённого хода внутри куска (стр. 691-706).

Узлы, которые в bspen были бы одной пачкой, в bscut — несколько кусков, но все шаги те же.

### Одна оговорка: флаг `blockedToMove`

Флаг не входит в ключ посещённости (стр. 420). Узел с `blockedToMove = true` — это вход в бесконечный хвост
занятой цели, из него можно только ждать, ходить нельзя. Если такой узел отмечен раньше, то обычный вход (из
которого ходить можно) в ту же пачку на том же или более позднем шаге будет отброшен правилом (А). Это было бы
потерей. Так же устроен и исходный Bulk Search (`src/flow-bs.cpp`, стр. 150-157), так что это не наше изменение.
Доказательства, что так не бывает, у меня нет. Проверено замером: в сборке с счётчиками такие отбрасывания
считаются (`flag_prune`). Во всех прогонах ниже их **0**. Догадка: с явными ожиданиями в занятой цели
(`explicitGoalWaits`, стр. 451-456) такой хвост — цепочка пачек длины 1, и обычный вход туда попадает не позже
флагового.

### Маленькая карта, где поздний вход раскрыт первым

Специально строить её не пришлось: в случайных задачах на коридорах это происходит постоянно (счётчик
`late_first`, ниже). Во всех таких задачах T совпал с перебором.

## 4. Верхняя граница T (cbm.cpp 653)

Нижний уровень ищет T от `minT` до `maxT = w·h + k + last` и, если не нашёл, отвечает «команда не решается».
Здесь k — роботы команды, `last` — самый большой шаг t среди её запретов (cbm.cpp 644-648). Если бы
настоящий минимальный T* был больше `maxT`, ребёнок CBM был бы отброшен зря. Ниже доказано, что так не бывает.
Тот же текст стоит комментарием над `solveTeam`.

**К какому ходу относится запрет на ребро с шагом t.** К ходу t → t+1. Это видно в трёх местах:
- `addEdgeConstraint`, bs_team.hpp 264: «the team may not move from -> to between steps t and t+1 (no flow on
  (from, 2t+1) -> (to, 2t+2))»;
- проверка хода `isForbidden(ts)` = `count(ts / 2 - 1)` для входа ts = 2(t+1) (стр. 692);
- конфликт в cbm.cpp 68: «swap: move t -> t+1».

Запрет на клетку с шагом t запрещает быть в ней на шаге t. Значит, начиная с шага last + 1, ничего не запрещено:
ни положения, ни ходы.

**Доказательство.** Пусть команда решается, T* — минимальный makespan. V — число свободных клеток, V ≤ w·h.
1. Если T* ≤ last + 1, то T* ≤ maxT, так как k ≥ 1 и V ≥ 1.
2. Пусть T* > last + 1. Возьмём положения роботов оптимального решения на шаге last + 1. Из них роботы как-то
   доходят до целей (хвост решения), и запретов там уже нет. Значит, это решаемая задача для неразличимых роботов
   без запретов.
3. По Yu, LaValle, «Multi-agent Path Planning and Network Flow» (WAFR 2012, arXiv 1204.5717) у такой задачи есть
   решение длиной не больше k + V − 1. Если карта несвязна, то в каждой компоненте k_c + V_c − 1 ≤ k + V − 1.
4. Их модель строже нашей: там запрещены встречные обмены, а у нас внутри команды они разрешены. Значит, их
   решение годится и у нас.
5. Склеим первые last + 1 шагов оптимального решения и это короткое решение. Получится решение с запретами длиной
   не больше last + 1 + k + V − 1 = last + k + V.
6. Значит, T* ≤ last + k + V ≤ w·h + k + last = maxT.

Граница с ходом t → t+1 получилась last + k + V, на 1 больше, чем было бы для хода t − 1 → t (last + k + V − 1).
