# Неделя 7, этап C1: аудит оптимальности по makespan

Что требуется: ни одно наше изменение не должно менять найденный T (makespan), и это должно быть видно либо из кода,
либо из проверки перебором. Код в этом этапе не менялся. Строки — по коммиту a70d321.

Слова, которые нужны ниже:
- **сеть «клетка × время»**: вершина — (клетка, шаг). Bulk Search ищет в ней пути от стартов до целей так же, как
  алгоритм максимального потока: каждый найденный путь добавляет одного робота, путь может «отменять» части уже
  проложенных путей (обратные рёбра);
- **пачка (bulk)**: отрезок шагов одной клетки, через который подряд не проходит ни один уже проложенный путь
  (`blocks[cell]` — шаги, где клетка занята). Вершины пачки соединены бесплатными ожиданиями, поэтому Bulk Search
  раскрывает пачку целиком одним узлом очереди: «вход в момент t» значит «доступны шаги от t до конца пачки»;
- **кусок (bscut)**: пачка, дополнительно разрезанная мягкими разрезами (`softCuts`): шаги, когда в клетке чужой
  робот. Кусок раскрывается одним узлом так же, как пачка;
- **посещённость**: `visitedTimeSTeps[cell]` — шаги, с которых клетку уже раскрывали в этом поиске.

## 1. Главный вопрос: может ли поздний дешёвый вход закрыть пачку и потерять пути

### Ответ

**Нет, не может.** Поздний вход закрывает только шаги от себя и дальше. Более ранний вход в ту же пачку после этого
не отбрасывается, а раскрывает оставшийся кусок «от себя до позднего входа − 1». Вместе они покрывают те же шаги,
что покрыл бы один ранний вход. Порядок очереди (штраф у bspen и bscut, `timeStep + h` у bs) влияет только на то,
*какой* путь найдётся, но не на то, *найдётся ли* он. Значит, при данном T ответ «пути нет» одинаков для всех
трёх вариантов. Это та же проверка, что в исходном Bulk Search, разница только в порядке очереди.

### Код (bs_team.hpp)

Посещённость хранится как множество шагов. Ключ сравнения — только шаг (стр. 420):
```cpp
bool operator<(const TimestepCostPair &b) const { return timeStep < b.timeStep; }
```
Порядок очереди: штраф первым, потом `key = timeStep + h` (стр. 431). Для bs штраф всегда 0.
```cpp
bool operator()(const Node &a, const Node &b) const { return a.pen != b.pen ? a.pen > b.pen : a.key > b.key; }
```
Проверка при снятии узла с очереди, `checkTimestepAndGetUnvisitedSafeInterval` (стр. 552-588):
```cpp
int prevBlock = -1, nxtBlock = maxTimestep;          // границы пачки, в которой лежит шаг ts
...
if (cutMode)                                          // bscut: границы куска, а не пачки
{
    nxtBlock = min(nxtBlock, nextSoftCut(cellID, timeStepCostPair.timeStep));
    prevBlock = max(prevBlock, prevSoftCut(cellID, timeStepCostPair.timeStep));
}
auto itrt = visitedTimeSTeps[cellID].upper_bound(TimestepCostPair(timeStepCostPair.timeStep));
if (itrt != visitedTimeSTeps[cellID].begin())
{
    --itrt;
    if (itrt->timeStep > prevBlock)                   // (А) в этой пачке уже был вход не позже ts
        return make_pair(false, Interval());
    ++itrt;
}
if (itrt != visitedTimeSTeps[cellID].end() && itrt->timeStep <= nxtBlock)
{                                                     // (Б) в этой пачке был вход ПОЗЖЕ ts
    nxtVisitedTimestep = itrt->timeStep;
    return {true, Interval(timeStepCostPair.timeStep, nxtVisitedTimestep - 1)};
}
return {true, Interval(timeStepCostPair.timeStep, nxtBlock)};
```
Отметка ставится после раскрытия (стр. 944): `visitedTimeSTeps[currentCell].insert(timeStepCostPair);`.
Проверка при добавлении в очередь `checkTimestep` (стр. 589-610) — то же правило (А).

### Разбор по шагам

Пусть в пачке (или куске) с границами (prevBlock, nxtBlock] есть вход e (ранний) и вход l (поздний), e < l.

1. Сначала раскрыт l (у него меньше штраф). Он получает отрезок [l, nxtBlock] и отмечает шаг l.
2. Потом снимается e. Правило (А) смотрит на последний отмеченный шаг ≤ e. Шаг l больше e, поэтому (А) не
   срабатывает, и e **не отбрасывается**. Срабатывает (Б): e получает отрезок [e, l − 1].
3. Вместе: [e, l − 1] ∪ [l, nxtBlock] = [e, nxtBlock]. Это ровно то, что дал бы один e, раскрытый первым.

Правило (А) отбрасывает вход только тогда, когда в той же пачке уже раскрыт вход **не позже** его. Значит, его
шаги уже покрыты. Так получается, что в любой момент раскрытые шаги пачки — это [самый ранний раскрытый вход,
конец пачки]. Это не зависит от порядка снятия.

Почему от порядка не зависит и сам ответ «путь есть / пути нет»:
- из раскрытого отрезка [l, h] следующие узлы строятся только по клетке, отрезку и флагу `blockedToMove`
  (ходы в соседей `getAllTimeSteps`, обратное ожидание, стр. 953-956; переход через мягкий разрез, стр. 948-951).
  Штраф на это не влияет, он только складывается в поле `pen`;
- если отрезок разбит на два, [e, l − 1] и [l, h], то каждый ход из исходного отрезка есть в одной из половин.
  Узлов в очереди может стать больше, но ни один шаг не теряется;
- значит, поиск обходит все шаги сети, достижимые из стартов. Это обычный поиск в графе, и порядок обхода на
  множество достижимых вершин не влияет. Сток (свободная цель, стр. 938-943) достижим при любом порядке или ни при
  каком. Поиск останавливается на первом найденном стоке, а это зависит только от достижимости;
- каждый найденный путь увеличивает поток на 1. Максимальный поток не зависит от того, в каком порядке находились
  увеличивающие пути. Значит, «вся команда дошла за T» тоже не зависит от порядка, и T тот же.

bscut отличается только тем, что пачка разрезана на куски (`prevSoftCut`/`nextSoftCut`). Для куска верно то же
рассуждение, а переходы между кусками есть явно:
- ожидание через разрез (стр. 948-951);
- вход в начало каждого куска `max(soft + 1, firstMove)` (стр. 620-628);
- обход запрещённого хода внутри куска (стр. 691-706).

Узлы, которые в bspen были бы одной пачкой, в bscut — несколько кусков, но все шаги те же.

### Одна оговорка: флаг `blockedToMove`

Флаг не входит в ключ посещённости (стр. 420). Узел с `blockedToMove = true` — это вход в бесконечный хвост
занятой цели, из него можно только ждать, ходить нельзя. Если такой узел отмечен раньше, то обычный вход (из
которого ходить можно) в ту же пачку на том же или более позднем шаге будет отброшен правилом (А). Это было бы
потерей. Так же устроен и исходный Bulk Search (`src/flow-bs.cpp`, стр. 150-157), так что это не наше изменение.
Проверено замером: в сборке с счётчиками такие отбрасывания считаются (`flag_prune`). Во всех прогонах ниже их
**0**. Подробный разбор — в разделе 5.

**Закрыто правкой d33469d** (раздел 5): флаговые входы отмечаются отдельно, и правило (А) больше не отбрасывает
обычный вход из-за флагового. Оговорка снята.

### Маленькая карта, где поздний вход раскрыт первым

Специально строить её не пришлось: в случайных задачах на коридорах это происходит постоянно (счётчик
`late_first`, ниже). Во всех таких задачах T совпал с перебором.

## 4. Верхняя граница T (cbm.cpp 653)

Нижний уровень ищет T от `minT` до `maxT = w·h + k + last` и, если не нашёл, отвечает «команда не решается».
Здесь k — роботы команды, `last` — самый большой шаг t среди её запретов (cbm.cpp 644-648). Если бы
настоящий минимальный T* был больше `maxT`, ребёнок CBM был бы отброшен зря. Ниже доказано, что так не бывает.
Тот же текст стоит комментарием над `solveTeam`.

**К какому ходу относится запрет на ребро с шагом t.** К ходу t → t+1. Это видно в трёх местах:
- `addEdgeConstraint`, bs_team.hpp 264: «the team may not move from -> to between steps t and t+1 (no flow on
  (from, 2t+1) -> (to, 2t+2))»;
- проверка хода `isForbidden(ts)` = `count(ts / 2 - 1)` для входа ts = 2(t+1) (стр. 692);
- конфликт в cbm.cpp 68: «swap: move t -> t+1».

Запрет на клетку с шагом t запрещает быть в ней на шаге t. Значит, начиная с шага last + 1, ничего не запрещено:
ни положения, ни ходы.

**Доказательство.** Пусть команда решается, T* — минимальный makespan. V — число свободных клеток, V ≤ w·h.
1. Если T* ≤ last + 1, то T* ≤ maxT, так как k ≥ 1 и V ≥ 1.
2. Пусть T* > last + 1. Возьмём положения роботов оптимального решения на шаге last + 1. Из них роботы как-то
   доходят до целей (хвост решения), и запретов там уже нет. Значит, это решаемая задача для неразличимых роботов
   без запретов.
3. По Yu, LaValle, «Multi-agent Path Planning and Network Flow» (WAFR 2012, arXiv 1204.5717) у такой задачи есть
   решение длиной не больше k + V − 1. Если карта несвязна, то в каждой компоненте k_c + V_c − 1 ≤ k + V − 1.
4. Их модель строже нашей: там запрещены встречные обмены, а у нас внутри команды они разрешены. Значит, их
   решение годится и у нас.
5. Склеим первые last + 1 шагов оптимального решения и это короткое решение. Получится решение с запретами длиной
   не больше last + 1 + k + V − 1 = last + k + V.
6. Значит, T* ≤ last + k + V ≤ w·h + k + last = maxT.

Граница с ходом t → t+1 получилась last + k + V, на 1 больше, чем было бы для хода t − 1 → t (last + k + V − 1).
Она всё равно не больше `maxT`, потому что V ≤ w·h. Код не менялся.

Та же граница стоит в cbm.cpp 478 (`checkPenalty`, только для диагностики `--pen-gap`), на найденный T она не
влияет.

## 5. Флаг `blockedToMove` в посещённости

Вопрос: может ли флаговый вход (из него можно только ждать) отбросить правилом (А) обычный вход в ту же пачку на
том же или более позднем шаге? Строки — bs_team.hpp до правки (a615290). Итог: доказательства для всех случаев не
нашлось, и посещённость исправлена (d33469d, подраздел «Правка d33469d»).

### Где создаётся флаговый узел

Флаг ставится только в трёх местах.
1. **Последний отрезок занятой цели** (`getAllTimeSteps`, стр. 640-643): при ходе в соседнюю клетку G входы
   перебираются по пачкам G. Хвост после последнего блока, который не меньше текущего входа, помечается флагом,
   если G — занятая цель (`timeAssigningGoalCell[G] < INF`).
2. **Отмена хода из занятой цели** (стр. 651-654): поиск идёт назад по чужому ходу G → сосед, и этот ход сделан на
   шаге не раньше `timeAssigningGoalCell[G]`.
3. **Цепочка** (стр. 958-963): флаговый узел с отрезком [ts, h] добавляет флаговый вход ts + 2, если ts + 2 ≤ h.

Что делает флаговый узел при раскрытии:
- не ходит в соседей (стр. 958-964, ветка `else` пропускается);
- не переходит через мягкий разрез (стр. 948);
- может «отменить ожидание» назад во времени (обратное ожидание, стр. 953-956), и этот вход уже обычный.

Важно, есть ли у команды запреты: любой запрет включает `explicitGoalWaits` (стр. 258, 267). Тогда ожидание
робота в занятой цели записано явно, шаг за шагом до `maxTimestep` (`makeGoalWaitsExplicit`, стр. 808, 821-839).
Без запретов работает код исходного Bulk Search без изменений.

### Команда с запретами (`explicitGoalWaits = true`): источники 1 и 3 доказаны

Обозначения: `maxTimestep` = 2T − 1, слой шага T — это индекс 2T = `maxTimestep` + 1.

**Свойство И.** У каждой занятой цели G есть блок на индексе ≥ `maxTimestep`. Почему:
- когда цель занимают, блоки ставятся с `timeAssigningGoalCell` до `maxTimestep` (стр. 803-808);
- когда T растёт, `extendGoalWaits` дописывает их до нового `maxTimestep` (стр. 831-839, вызывается в `solve`);
- блок x убирает только отмена ожидания x → x+1 (стр. 783), то есть путь, который прошёл через (G, x+1). При
  этом тот же путь в стр. 764-774 ставит ожидания и блоки до x+1 включительно, если их там не было. Значит, блок
  `maxTimestep` может пропасть, только если появился блок `maxTimestep` + 1. А блок `maxTimestep` + 1 не убирается:
  для этого нужен узел на `maxTimestep` + 2, а он вне сети.

**Где тогда флаговые узлы.**
- Источник 1: флаг получает только вход, после которого у G нет ни одного блока
  (в варианте с разрезами `nextHardBlock` = INF, стр. 546-550; разрезов после `timeAssigningGoalCell` нет, стр. 518).
  По свойству И такой вход больше `maxTimestep`. Вход в соседа не дальше `it.h + 1` ≤ `maxTimestep` + 1
  (стр. 645-666). Значит, флаговый вход из источника 1 всегда ровно на индексе 2T.
- Источник 3 из такого узла не срабатывает: нужно ts + 2 ≤ h ≤ `maxTimestep`.

**Обычных входов на индекс 2T в ту же пачку G не бывает.** Все места, где кладётся вход без флага:
- старты: индекс 0;
- обычные входы `getAllTimeSteps`: каждый лежит в пачке, которая кончается блоком не раньше него, а флаговая пачка
  лежит после последнего блока;
- источник 2 без флага: индекс < `timeAssigningGoalCell` ≤ `maxTimestep`;
- обратное ожидание: l − 1 ≤ `maxTimestep`;
- переход через мягкий разрез: h + 1, где h — разрез < `maxTimestep`;
- обход запрещённого хода и второй кандидат bscut (стр. 694-716) сохраняют флаг входа и не выходят из его куска.

Значит, правило (А) не может отбросить обычный вход флаговым из источников 1 и 3.

**Измерено** (отладочная сборка вне репозитория, печать каждого флагового входа при `explicitGoalWaits`;
`test_corridors.py low`, 3 × 1000 задач, все четыре варианта bs): 49 853 флаговых входа, все на индексе
`maxTimestep` + 1, у всех последний блок цели = `maxTimestep`. Это согласуется с доказательством.

### Что не доказано

**(а) Источник 2, отмена хода из занятой цели, в обоих режимах. Закрыто правкой d33469d.** Нужен уже проложенный ход из G на шаге
≥ `timeAssigningGoalCell[G]`. Узел из этого источника может попасть в любую пачку G, не только в последнюю.
Доказательства нет. Измерено: счётчик `flag_cancel` = 0 во всех прогонах (300 задач `test_corridors.py low` с
запретами и 2000 без запретов, ниже). Догадка: при запретах путь, проходящий через G после
`timeAssigningGoalCell`, сдвигает `timeAssigningGoalCell` вперёд (стр. 764-774), и такой ход оказывается раньше
него.

**(б) Команда без запретов (код исходного Bulk Search). Закрыто правкой d33469d.** Здесь хвост занятой цели после `timeAssigningGoalCell` —
одна бесконечная пачка без явных ожиданий. Отбрасывание возможно в таком порядке:
1. Флаговый вход e' (поздний) раскрыт раньше флагового e < e' − 1. Так бывает, когда e ещё не был в очереди.
2. Раскрытие e' кладёт обычный вход e' − 1 (обратное ожидание: e' − 1 ≥ `timeAssigningGoalCell`).
3. Затем раскрыт e и отмечен.
4. Затем снимается e' − 1, и правило (А) его отбрасывает: отмечен e ≤ e' − 1.

Отброшенный узел означает «робот в цели уходит на шаге e' − 1, новый робот входит на шаге e'». В порядке «сначала
e» вход e' отбрасывается сам, и узел e' − 1 вообще не появляется. Поэтому такое отбрасывание даёт ровно то, что дал
бы порядок «сначала e». Он не слабее порядка исходного Bulk Search, но и не сильнее. Теряет ли сам исходный
алгоритм пути при каком-то порядке, этим не доказано.

**Измерено** (`archive/flag_noconstr.py`: 2000 задач без запретов на тех же картах, 2-6 роботов, 1-5
чужих роботов, старт T = 1, против перебора):

| вариант | флаговых входов положено | раскрыто | `flag_cancel` | `flag_prune` | расхождений T |
|---|---|---|---|---|---|
| bs | 6131 | 3367 | 0 | 0 | 0 |
| bspen | 6509 | 4183 | 0 | 0 | 0 |
| bscut | 6639 | 4174 | 0 | 0 | 0 |

Контрпример (задача, где T отличается от перебора) не найден.

### Правка d33469d

**Что сделано.** Раскрытые флаговые входы отмечаются в отдельном множестве `visitedBlocked[cell]`, обычные — как
раньше, в `visitedTimeSTeps[cell]`.
- Правило (А), отбросить вход: обычный вход отбрасывается, только если в его пачке уже раскрыт **обычный** вход на
  том же или более раннем шаге; флаговый — если раскрыт вход любого вида.
- Правило (Б), обрезать отрезок перед следующим раскрытым входом той же пачки: по входам **обоих** видов, как в
  исходном Bulk Search.
- Места: `coveredBy` и `nextVisited` (новые), `checkTimestepAndGetUnvisitedSafeInterval`, `checkTimestep`, отметка
  после раскрытия.

**Почему правило (Б) оставлено по обоим множествам.** Первый вариант правки не давал флаговому входу и обрезать
отрезок обычного. Он ломал поток. В `test_corridors.py low` (seed 7) на карте-кресте 5×5 без запретов bscut нашёл
T = 3, но при разборе потока из клетки (2,3) выходили два пути (exit 3, «2 flow edges leave»). У старого кода на
этой задаче `flag_prune` = 0 и `flag_trunc` = 3: отбрасываний не было, менялась только обрезка. Причина:
- без запретов ожидание робота в занятой цели не записано в `blocks`. Блок есть только на шаге прихода
  (`timeAssigningGoalCell`, стр. 804), а дальше хвост — одна пачка до `maxTimestep`;
- обычный вход в этот хвост бывает только один: обратное ожидание l − 1 (стр. 953-956). Его кладёт раскрытие
  флагового входа l, то есть l к этому моменту уже отмечен. Все входы ходом в хвост — флаговые (источник 1);
- правило (Б) обрезает отрезок такого входа перед l, получается [l − 1, l − 1]. Смысл: «робот в цели уходит ровно
  на шаге l − 1, новый занимает цель с шага l». Без обрезки отрезок тянется до конца хвоста. Но это ожидания,
  которые занимает робот в цели, и путь через них даёт неправильный поток.

Значит, отметка флагового входа в правиле (Б) — не отсечение лишнего, а часть того, как исходный Bulk Search
описывает занятый хвост. Обрезка не зависит от порядка очереди: l всегда отмечен раньше, чем снимается l − 1.
Фраза прежней редакции «пока `flag_prune` = 0, правка не меняет ни одного раскрытия» верна для принятого
варианта, а для первого была неверна.

**Доказательство.** Нужно показать: ни при каком порядке очереди правило посещённости не убирает шаг сети,
достижимый из стартов. Тогда работает рассуждение раздела 1: поиск обходит все достижимые шаги, сток находится при
любом порядке или ни при каком, и T от порядка не зависит.
1. *Правило (А).* Пусть вход x (клетка c, шаг ts) отброшен из-за раскрытого входа y той же пачки, шаг y ≤ ts.
   После правки либо y обычный, либо x флаговый. В обоих случаях y умеет не меньше x:
   - y обычный, x любой. Шаги отрезка x лежат в отрезке y или в отрезках более поздних раскрытых входов, перед
     которыми y обрезан (раздел 1, шаг 3). Ходы в соседей из этих шагов уже сделаны. Обратное ожидание x (шаг
     ts − 1): если ts больше шага y, то ts − 1 тоже внутри этого покрытия; если ts равен шагу y, то y кладёт то
     же обратное ожидание. Цепочка ts + 2 флагового x идёт внутри той же пачки и тоже покрыта;
   - x и y флаговые. Флаговый вход умеет только две вещи: цепочку ts + 2 внутри пачки и обратное ожидание.
     Рассуждение то же.

   Значит, отброшенный вход не даёт ни одного шага, которого не дали бы уже раскрытые.
2. *Правило (Б).* Обрезка обычным входом — раздел 1, шаг 3: [e, l − 1] ∪ [l, конец] = [e, конец]. Обрезка
   флаговым входом бывает только в хвосте занятой цели без явных ожиданий. В режиме с запретами флаговые входы
   стоят только на индексе 2T, за последним блоком, и обычных входов там нет (подраздел про
   `explicitGoalWaits`). В хвосте обрезка даёт ровно тот отрезок, который в сети доступен. Шаги, которые она
   отрезает, — занятые ожидания, а не потерянные.
3. Рассуждение не использует, откуда взялся флаговый вход. Поэтому оговорки (а), источник 2, и (б), команда без
   запретов, закрыты.

Как и раздел 1, это рассуждение о посещённости и порядке очереди. Сами правила переходов (какие ходы и обратные
рёбра есть в сети) взяты из исходного Bulk Search и здесь не доказываются.

**Чем отличается от кода этапа B.** Только там, где старый код отбрасывал обычный вход из-за флагового, то есть
где `flag_prune` > 0. В остальных случаях раскрытия те же.
